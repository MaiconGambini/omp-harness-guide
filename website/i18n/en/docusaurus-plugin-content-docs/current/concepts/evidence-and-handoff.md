# Evidence and Handoff

The evidence and handoff discipline establishes the verifiable chain of execution proofs and the durable state transfer protocol between consecutive agent sessions.

A trustworthy technical completion does not stem from a conversational chat assertion ("tests passed and everything looks good"). The harness mandates an auditable evidence chain connecting original intent to terminal execution commands and disk-persisted reports.

The handoff converts this ephemeral evidence into durable state consumable by future sessions, ensuring continuity without context loss.

## The five rungs of evidence

Evidence rungs are cumulative and classify the rigor behind any completion claim:

| Rung | Proof type | What it demonstrates |
|---|---|---|
| **Rung 1 — Assertion** | Text emitted by an agent asserting completion. | Model intent or expectation; does not prove execution. |
| **Rung 2 — Artifact** | Written files, diffs, or generated schemas. | What changed in the working tree; does not demonstrate functionality. |
| **Rung 3 — Command output** | Captured output and exit code from a command. | Reproducible execution of a linter, compiler, or unit test suite. |
| **Rung 4 — Acceptance** | Table mapping acceptance criteria to results. | Explicit fulfillment of agreed specification requirements. |
| **Rung 5 — Live verification** | System running in terminal with real traffic exercised. | End-to-end functional behavior observed with HTTP codes and logs. |

A lower rung never substitutes for a higher rung: an assertion (Rung 1) or an edited file (Rung 2) carries zero evidentiary value without real execution output (Rung 3 or 5).

## Quality Gate report as evidence

During the validation phase, evidence is aggregated into a structured Quality Gate report generated by the orchestrator. This immutable artifact records:

- The exact working tree state hash (`sourceHash`).
- The diff risk classification (`low`, `medium`, or `high`) and matching governance tier (`auto`, `sampling`, or `full`).
- The metric table containing observed values and tolerance thresholds.
- The explicit measurement coverage label: **`Measured: N/M`**.

```text
- Verdict: **pass** (exit 0)
- Measured: 8/28 metrics
- WARNING: most metrics unmeasured (8/28); pass is not evidence of quality
```

The `Measured: N/M` indicator prevents reports with dozens of disabled or unconfigured metrics from being misrepresented as complete quality verification.

## Commit trailer bound to sourceHash

When an initiative is approved for merging into Git history, the delivery commit receives formal metadata in its footer (*commit trailers*). This cryptographic link proves the commit matches the approved gate report:

```gitcommit
feat: add session token expiration handler

Implement automatic session invalidation upon credential revocation.
Closes #142.

Quality-Gate: pass (full)
Metrics: regression=0
Adherence: rules-active=0
Risk-Tier: full
Gate-Report: <relative-path>/quality-report.json
Source-Hash: 6ed19345c071fc94
```

This binding enables automated auditing months later to confirm whether a production commit was actually tested or if gate checks were bypassed.

## Role separation: Judge and Refine

During validation and confirmation, evidence is processed by specialized agents maintaining strict role separation:

![Judge and Refine inner workings](/omp-harness-guide/img/diagrams/judge-refine-a2a.png)
*How the Judge and Refine agents operate on evidence reports.*

- **The Judge (read-only):** Compares the original specification, file diffs, and the Quality Gate report. It produces a formal JSON receipt with a verdict (`accept`, `revise`, or `reject`) and explicitly lists any blocking criteria.
- **The Refine agent (read-only):** Reviews review findings to propose architectural pattern improvements. The Refine agent cannot edit source code, cannot alter the Judge's verdict, and requires human operator confirmation for its proposals.

## Session handoff structure

Whenever a development cycle pauses or concludes, the orchestrator writes `docs/harness/session-handoff.md`. The document requires five mandatory sections:

```markdown
# Handoff — <initiative title> (<date>)

## Verified Now
Concise summary of verified accomplishments:
- Risk (`low`, `medium`, or `high`), evaluated tier (`auto`, `sampling`, or `full`), and Quality Gate result (e.g., sourceHash 6ed19345, verdict pass).
- Exact coverage label: `Measured: N/M`.
- Executed automated tests and pass counts.

## Changed This Session
Surgical list of modified files, new artifacts, and altered contracts.

## Broken Or Unverified
Strict transparency regarding what was NOT verified:
- Metrics returning `unavailable` or `not_configured`.
- Coverage warnings (e.g., fewer than half of metrics measured).
- Pending tests or behaviors still requiring live staging validation.

## Decisions Made
Architectural design choices, library selections, or conventions that the next session must respect.

## Next Best Step
Exactly ONE actionable next step, noting prerequisites or suggested commands.
```

The `session-handoff.md` ensures that a new agent or developer resuming work the following morning needs no conversational re-briefing or historical context hunting.

## Inter-lane evidence envelope

When the orchestrator dispatches parallel tasks to subagents (`tasks[]`), each lane returns a compact four-key envelope:

```json
{
  "status": "ok",
  "summary": "Parser implementation completed with passing tests",
  "artifact": "local://lane-parser-report.md",
  "failures": []
}
```

Subagents do not invent file lists or global next steps; the parent orchestrator reconciles individual envelopes and synthesizes the unified handoff.

## What this proves and what it does not prove

### What it proves
- That completion claims are anchored in real program output and Git hashes.
- That measurement gaps (`Broken Or Unverified` and `Measured: N/M`) are visible to reviewers.
- That repository state survives agent compactions and context window resets deterministically.

### What it does NOT prove
- A well-written handoff **does not prove** the system is bug-free if underlying test suites were superficial.
- It does not replace critical human review of architectural decisions.
- It does not guarantee remote third-party branches will merge cleanly without upstream conflicts.
